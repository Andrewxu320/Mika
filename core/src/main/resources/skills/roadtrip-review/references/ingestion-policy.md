# 行程摄取与确认策略

## 提取草案

仅提取用户明确说明的日期、参与人数、车辆约束、按顺序排列的地点、计划过夜点和硬性约束。立即分配稳定 ID。将省略的可选值记录为 `null`，并添加一条 `unknowns` 记录；绝不编造出发时间、续航里程、坐标或过夜点。

为每项事实标注来源：`user`、`external`、`calculation` 或 `inference`。建议的过夜点属于 `inference`，不能仅因其便于安排行程就变为已确认内容。

## 实质性歧义关卡

只要歧义可能改变路线几何、时间安排、限制或风险，就转入 `drafted -> awaiting-confirmation`。实质性歧义包括重名地点、途经点顺序不清、过夜城市不确定、日期冲突，或一个道路名称对应多个路段。展示排序后的草案，并提出有针对性的问题。在歧义解决前，不得研究受影响的行程路段。

示例：

- 地点歧义：“新都”可能指成都市新都区，也可能指另一个同名地点。保留两个候选项，并请用户选择。
- 缺失值：省略的车辆续航里程应记为 `null`，并添加一条 `unknowns` 记录。除非路线需要判断续航，否则不应因此阻止确认。
- 推断的过夜点：如果多日行程清单列出了途经点，但未指定住宿城市，应将建议的过夜城市保留为 `inference`，并在研究前请用户确认。不得暗中将其提升为已确认停靠点。

## 确认与恢复

确认必须涵盖按顺序排列的停靠点、日期、过夜点和硬性约束。记录 `confirmedAt`，创建一个修订版本，然后转入 `confirmed`。恢复时读取 `trip.state`：若为 `awaiting-confirmation`，继续待完成的确认；只有在 `confirmed` 后才检查能力；如果存在有效的后续状态和产物，绝不重复已经完成的外部工作。

## 隐私最小化

从持久化数据中移除姓名、电话号码、身份证件、预订编号、精确家庭住址和车辆号牌。如果提供商操作需要车辆号牌且用户选择提供，只能将其用于该次操作，不得写入行程或证据。省略用户提供的详细信息时，应告知用户。
